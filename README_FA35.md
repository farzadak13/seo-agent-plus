# Stage 35 — صحت داده و جهت یادگیری

نصب‌کننده پیش از نوشتن، همهٔ فایل‌های هدف را با Stage 34 مقایسه می‌کند. در صورت اختلاف کد، هیچ فایلی تغییر نمی‌کند. تفاوت CRLF/LF و فضای خالی ابتدا و انتهای فایل نادیده گرفته می‌شود. نسخه‌های اصلی در stage35_backup_* نگهداری می‌شوند.

## رفتار اصلاح‌شده

### یادگیری Position

کاهش عدد Position بهبود محسوب می‌شود؛ جهت سیگنال و تغییر اولویت هر دو اصلاح شده‌اند. average_relative_change همچنان تغییر عددی خام را نگه می‌دارد؛ مثلاً تغییر ۱۰ به ۵ برابر منفی ۰٫۵ است، اما سیگنال آن مثبت و اثر آن روی اولویت افزایشی است. رفتار CTR و سقف تغییر اولویت حفظ شده‌اند.

تکرار یک feedback_id با دادهٔ یکسان فقط یک نمونه حساب می‌شود؛ اختلاف محتوا زیر یک شناسه رد می‌شود. این سیاست بر پایهٔ feedback_id است، نه action_id؛ تولیدکنندهٔ feedback باید هویت پایدار به هر رویداد بدهد. برای اصلاح سیگنال‌های Position ذخیره‌شدهٔ قدیمی، LearningContext را از feedbackهای اصلی بازسازی کنید؛ migration خودکار داده‌های قدیمی در این بسته نیست.

### ردیف‌های GSC

- یک کلید خام تکراری با clicks/impressions/position یکسان، یک‌بار شمارش می‌شود.
- همان کلید با مقادیر متفاوت باعث خطا می‌شود؛ مقدار دلخواه انتخاب نمی‌شود.
- کلیدهای خام متفاوت که بعد از نرمال‌سازی به یک URL/query/date برسند، تجمیع می‌شوند. Position با وزن impressions ترکیب می‌شود؛ نبود Position برای بخشی از impressions باعث نتیجهٔ نامعلوم می‌شود.
- تاریخ‌ها و هدف‌های متفاوت جدا می‌مانند. ورودی تغییر داده نمی‌شود.
- counts نامعتبر، clicks بیشتر از impressions، Position نامتناهی/NaN و ترتیب dimensions نامناسب رد می‌شوند.
- قرارداد قدیمی query با دو کلید و fetch_date همچنان پشتیبانی می‌شود. قرارداد جدید live دارای dimensions صریح است.

### آمار مستقل URL و بازه‌ها

برای هر Run چهار جریان درخواستِ دارای صفحه‌بندی وجود دارد:

۱. baseline با page/query/date
۲. baseline با page/date
۳. current با page/query/date
۴. current با page/date

پس در مقایسه با Stage 34 حداقل تعداد درخواست‌ها از دو به چهار افزایش می‌یابد؛ هر جریان می‌تواند چند صفحه داشته باشد. URL totals از پاسخ مستقل گرفته می‌شوند، نه جمع queryهای دریافتی. هر چهار پاسخ ذخیره می‌شوند و یک runtime_data_bundle هویت و بازه‌های آن‌ها را به Snapshot متصل می‌کند.

برای URL هدف، مجموع تمام queryهای دریافتی در هر روز با URL totals همان روز مقایسه می‌شود. اختلاف روزها اجازه ندارد در جمع کل خنثی شود. query کمتر از URL یک پوشش جزئی مجاز است؛ query بیشتر از URL یا نبود آمار مستقل URL برای روز query مشاهده‌شده، تصمیم‌گیری را متوقف می‌کند. این خطا در lifecycle عادی Job/Run ثبت می‌شود؛ سیاست retry موجود تغییر نکرده است.

baseline بلافاصله پیش از current و با طول برابر ساخته می‌شود. روزهای query ناموجود همچنان MISSING_UNKNOWN هستند، نه صفر قطعی. Measurement نیز بازه‌های هم‌پوشان یا نابرابر را رد می‌کند و تاریخ تکراری را یک روز حساب می‌کند. مقایسهٔ مدت‌های مختلف در این مرحله پشتیبانی نمی‌شود؛ برای آن باید نرخ‌های روزانه یا سیاست جدا تعریف شود.

### دادهٔ نهایی و صفحه‌بندی

GSCClientConfig اکنون به‌صورت پیش‌فرض data_state="final" دارد؛ مسیر live تصمیم‌گیری نیز فقط همین حالت را قبول می‌کند. کلاینت عمومی برای کاربردهای دیگر می‌تواند صریحاً all بگیرد، ولی آن خروجی ورودی معتبر این مسیر تصمیم‌گیری نیست.

metadata تاریخ شروع دادهٔ ناقص در صفحه‌بندی حفظ می‌شود. اگر پاسخ با وجود درخواست final، بازهٔ ناقص را اعلام کند، یا نوع aggregation و بازه‌ها ناسازگار باشند، Run وارد تصمیم‌گیری نمی‌شود. dataState، dimensions و metadata جزئی از دادهٔ ذخیره‌شده و هویت پاسخ‌اند.

حد پیش‌فرض صفحه‌بندی ۱۰۰ صفحه است. تکرار کامل یک صفحه، تغییر aggregation بین صفحه‌ها، پاسخ بزرگ‌تر از rowLimit یا رسیدن به حد صفحه قبل از اثبات پایان، خطا می‌دهد؛ خروجی نیمه‌کاره به‌عنوان پاسخ کامل برگردانده نمی‌شود. max_pages در GSCClientConfig قابل تنظیم است؛ runtime فعلی مقدار پیش‌فرض را استفاده می‌کند.

این کنترل‌ها تضمین نمی‌کنند تمام queryهای Search Console در دسترس باشند. محدودیت‌های داخلی API همچنان وجود دارند و اختلاف مجاز query/URL به‌تنهایی خطای سیستم نیست.

## محدودیت‌ها و ادامه

- دریافت final به معنی جدیدترین روز ممکن یا کامل‌بودن همهٔ queryها نیست. روزهای ناموجود توسط کیفیت داده بررسی می‌شوند.
- تطبیق روزانه برای URL هدف است؛ این بسته ممیزی کل property نیست.
- سیاست‌های فعلی canonicalize_url/normalize_query حفظ شده‌اند. مواردی مثل مستقل‌بودن HTTP و HTTPS در یک سایت خاص ممکن است سیاست نرمال‌سازی اختصاصی بخواهند.
- سازگاری زمانی داده، اثبات اثر علّی تغییر سئو نیست؛ seasonality و آزمون کنترل‌شده هنوز در سنجش پیشرفته پوشش داده نشده‌اند.
- OAuth refresh، service account و sc-domain همچنان خارج از این بسته‌اند.
- کارخانهٔ چند CMS و الزام تأیید Action تغییر نکرده‌اند؛ تغییری روی سایت واقعی اجرا نمی‌شود.

قدم بعدی مسیر محصول، اتصال دادهٔ صفحه و SERP به پیشنهاد عنوان و LLM است؛ سپس API تأیید و اجرای کنترل‌شدهٔ همان پیشنهاد تکمیل می‌شود.

# نقشه راه — وضعیت واقعی و مسیر پیش رو

آخرین بازنویسی: ۲۴ شهریور ۱۴۰۵ (۱۵ سپتامبر ۲۰۲۶)

این سند جایگزین `AI_SEO_Agent_Stage33_and_Final_Roadmap.md` است. تفاوت اصلی‌اش
این است که وضعیت هر مرحله را بر اساس «چه چیزی واقعاً اجرا شده» می‌نویسد، نه
«چه چیزی کد شده».

---

## قاعده‌ای که از این به بعد رعایت می‌شود

یک مرحله وقتی Done است که **علیه چیز واقعی اجرا شده باشد**، نه علیه fake.

دلیل این قاعده یک تجربهٔ مشخص است: Stage 33 خودش را با معیار «درخواست API
واقعاً اجرا شود و بعد از restart اطلاعات بماند» تمام‌شده اعلام کرد و ۸۶۱ تست
سبز داشت. اولین باری که کد با یک PostgreSQL واقعی حرف زد، معلوم شد
`UNIQUE (record_id)` باعث می‌شده نسخهٔ دوم هر Site و Run و Job غیرقابل نوشتن
باشد — یعنی **تنظیم اتصال GSC، که دومین قدم هر onboarding است، هرگز کار
نمی‌کرده**. علتش این بود که `InMemoryRepository` چیزی را مجاز می‌دانست که
schema ممنوع کرده بود.

نتیجهٔ عملی: هر test double باید همان قیدهایی را اعمال کند که نسخهٔ واقعی
اعمال می‌کند. و هر مرحله‌ای که سرویس بیرونی دارد، تا وقتی با آن سرویس اجرا
نشده، «کدنویسی‌شده» است نه «تمام‌شده».

اینها از بررسی معماری بیرون آمدند و هیچ‌کدام در شماره‌گذاری ۳۳ تا ۴۳ جا

| کار | وضعیت |
| --- | --- |
| migration runner با ثبت و lock و تشخیص دستکاری | ✅ انجام شد |
| ستون و ایندکس tenant، کوئری صفحه‌بندی‌شدهٔ tenant-scoped | ✅ انجام شد |
| قید «مالک یک aggregate تغییرناپذیر است» | ✅ انجام شد |
| PostgreSQL محلی با docker compose، دو دیتابیس جدا | ✅ انجام شد |
| تثبیت وابستگی‌ها در pyproject | ✅ انجام شد |
| **هویت واقعی tenant** — مدل Tenant، کلید API هر مشتری، اعمال مالکیت | ⛔ مانده |
| **ذخیرهٔ رمزنگاری‌شدهٔ اعتبارنامه در دیتابیس** — الان افزودن سایت یعنی تغییر env و restart | ⛔ مانده |

## مسدودکننده‌های بیرونی

اینها با کد حل نمی‌شوند و تا روشن نشوند نمی‌شود به هیچ زمان‌بندی تعهد داد.

**۱. احراز هویت گوگل از ایران.** روش ورود (OAuth یا service account)، نوع
property (URL-prefix یا sc-domain)، و اینکه آیا اتصال مستقیم ممکن است یا باید
از VPS عبور کند. روی طراحی لایهٔ transport اثر مستقیم دارد.

**۲. منبع SERP.** هنوز انتخاب نشده. بدون آن Stage 36 در دنیای واقعی معنی
ندارد و Stage 38 هم شواهدی برای تصمیم نخواهد داشت. مسئله فنی نیست؛ دسترسی و
پرداخت از ایران است.

## چرا درصد کد با درصد کار یکی نیست

شاید ۶۰٪ کد نوشته شده ولی حدود ۳۰٪ کار انجام شده. مرحله‌های ۱ تا ۳۶ منطق خالص
بودند بدون وابستگی بیرونی — همان نوعی که سریع پیش می‌رود. چیزی که مانده عمدتاً
یکپارچه‌سازی، عملیات و تجربهٔ کاربری است، و این‌ها فشرده نمی‌شوند: از احراز
هویت گوگل، یک وردپرس بدقلق، یا کاربری که صفحه را نمی‌فهمد نمی‌شود با سرعت
بیشتر عبور کرد.

## ترتیب پیشنهادی

۱. **اسپایک دادهٔ واقعی GSC** — read-only، یک URL از pama.shop. هدف feature
   نیست؛ اعتبارسنجی فرضیات دادهٔ فارسی است: نرمال‌سازی query، URL های
   percent-encoded، sc-domain، حجم واقعی. بزرگ‌ترین ریسک باقی‌مانده را زودتر
   از همه باز می‌کند.

۲. **تصمیم SERP** — چون Stage 36 و 38 هر دو به آن گره خورده‌اند.

۳. **هویت tenant** — پیش‌نیاز Stage 37.

۴. از اینجا به بعد به ترتیب roadmap: ۳۷ تأیید، ۳۸ اجرا، ۳۹ سنجش.

توصیه: خط پایان ۱ را هدف بگیرید و محصول را چند ماه **واقعاً در PAMA استفاده
کنید** پیش از ساختن UI. تا وقتی خودتان روزمره با آن کار نکنید معلوم نیست UI
باید چه چیزی نشان دهد، و UI گران‌ترین قلم فهرست دوم است. رابط کاربری برای
محصولی که هنوز کسی با آن کار نکرده، تقریباً همیشه دو بار ساخته می‌شود.
